# Agent 도구·익스플로잇 변경 설명

이 문서는 이번 변경의 목적, 실행 흐름, 실제 확인 범위와 남은 한계를 팀원에게 설명하기 위한 자료입니다.

## 한눈에 보는 변경 이유

기존 Agent는 ELF 파일의 기본 정보와 함수·심볼을 확인할 수 있었지만, ROP 문제에서 자주 필요한 가젯 검색, 실행 중 레지스터 확인, 익스플로잇 실행 결과를 받는 기능이 부족했습니다. 그래서 이전에 풀었던 ROP Emporium 문제에서 실제 사용했던 분석 방법을 도구로 연결했습니다.

또한 여러 문제 파일을 Agent에 전달했을 때 바이너리와 `.so`, `flag.txt`가 서로 다른 임시 폴더로 복사되던 문제를 고쳤습니다. 파일들의 상대 폴더 구조를 유지해 대상 프로그램이 함께 제공된 파일을 찾을 수 있게 했습니다.

## Agent 실행 흐름

```text
agent.py
  └─ 문제 파일을 workspace의 임시 폴더에 구조를 유지해 복사
     └─ reliability.py
        └─ core.py가 모델 요청 → 도구 호출 → 결과 전달을 반복
           └─ tools.py의 실제 로컬 도구 실행
              └─ 모델이 결과를 보고 다음 도구나 최종 답변 선택
```

- `agent.py`: CLI 입력과 문제 파일을 처리하고, 문제 분석 지침과 결과 보고서 생성을 담당합니다.
- `providers.py`: Gemini 응답에서 텍스트와 구조화된 도구 호출을 읽어 Agent 형식으로 전달합니다.
- `reliability.py`: 도구 인자를 검사하고, 일시적인 오류 재시도·호출 기록을 처리합니다. 이번에 `run_exploit`의 문자열 배열 인자도 검증할 수 있도록 JSON Schema의 배열 처리를 추가했습니다.
- `core.py`: 모델이 요청한 도구를 실행하고 그 결과를 다시 모델에 전달합니다. Flag 형식의 문자열을 도구 결과에서 확인하면 성공을 반환합니다.
- `tools.py`: 파일·ELF 분석, 디버깅, 익스플로잇 저장과 실행 등 실제 도구 기능을 제공합니다.

## 추가·수정한 도구

| 도구 | 하는 일 | 필요한 상황 |
|---|---|---|
| `search_rop_gadgets` | ROPgadget으로 명령어 가젯을 검색합니다. 기본 20바이트 깊이로 ret2csu의 다중 pop 가젯을 포함하며, 깊이를 8~64바이트로 조정할 수 있습니다. | `pop rdi`, `xchg rsp`, CSU 가젯 등 ROP 체인 구성 |
| `dump_elf_section` | `.data`, `.init_array` 같은 ELF 섹션의 바이트와 주소를 확인합니다. | 문자열을 쓸 위치나 함수 포인터 배열 확인 |
| `search_elf_bytes` | 텍스트 또는 `hex:` 바이트열을 검색하고, 로드 구간에 해당하면 ELF 가상 주소를 계산합니다. | 문자열·데이터 위치 확인. PIE는 실행 베이스 주소를 별도로 알아야 합니다. |
| `debug_binary` | GDB에서 지정한 심볼·주소에 멈춰 레지스터, 명령어, backtrace를 확인합니다. 대상 바이너리의 폴더에서 실행해 주변 파일 의존성도 처리합니다. | 정적 분석만으로 레지스터 값이나 실행 경로를 알기 어려울 때 |
| `run_exploit` | `workspace/exploit.py`를 최대 60초 실행하고 종료 코드, 표준 출력, 오류를 Agent에 반환합니다. | 익스플로잇이 실패한 원인을 보고 수정·재시도할 때 |

`write_exploit`은 코드를 저장하고 문법을 확인합니다. 저장만으로는 성공을 뜻하지 않으며, 로컬 문제가 제공된 경우 Agent가 `run_exploit`을 호출해 결과를 확인하도록 지침을 바꿨습니다. 실패하면 오류를 다음 모델 요청에 전달하고 수정을 시도합니다.

`run_exploit`은 실행 시간 제한이 있는 로컬 실행 도구이며, 운영체제 수준의 격리 환경은 아닙니다. 허가된 로컬 워게임 코드에만 사용해야 합니다.

## 실제 검증

이전 풀이 파일이 있는 ROP Emporium x86-64 8문제에서 파일·보호기법·심볼·import/relocation·가젯·섹션·바이트 주소·GDB·cyclic offset 도구를 확인했습니다.

- `ret2win`, `split`, `callme`, `write4`, `badchars`, `fluff`, `pivot`, `ret2csu` 모두에서 문제별 핵심 가젯을 검색했습니다.
- 기존 `solve.py` 8개를 `run_exploit`으로 실행해 종료 코드 0과 Flag 출력을 확인했습니다.
- ret2csu 검색 실패 원인은 ROPgadget 기본 깊이 10바이트가 다중 pop 가젯을 포함하지 못한 것이었습니다. 기본 깊이를 20바이트로 바꾼 뒤 검색을 통과했습니다.
- `callme` 디버깅 실패 원인은 GDB 작업 폴더가 바이너리 폴더가 아니어서 `libcallme.so`를 찾지 못한 것이었습니다. GDB가 바이너리 폴더에서 실행되도록 바꿨습니다.
- 자동화 검사 15개가 통과했습니다.
- CLI가 사용하는 `run_agent_reliable` 흐름에서 의도적인 첫 실패 → 오류 전달 → 익스플로잇 재작성 → 재실행 → Flag 반환을 테스트용 호출 공급자로 확인했습니다.

테스트용 호출 공급자는 정해둔 도구 호출을 재생합니다. 따라서 이는 Agent·도구·오류 피드백의 연결 확인이며, LLM이 스스로 풀이를 추론했다는 증거는 아닙니다. Gemini 계산 도구의 실시간 왕복은 확인했지만, 실제 익스플로잇 생성 요청은 Gemini가 거부해 모델이 직접 작성한 익스플로잇의 성공 여부는 아직 확인하지 못했습니다.

## 현재 범위와 다음 과제

현재 검증 범위는 비-PIE x86-64 ELF 기반 ROP 문제입니다. 포맷 스트링, ret2libc/PIE, 힙, 32비트, 원격 서비스 문제에서의 분석 성공률은 아직 측정하지 않았습니다. MCP 연동이나 풀이 전략을 저장해 유사 문제에 재사용하는 Memory 기능도 이번 변경에는 포함되지 않았습니다.

다음 검증은 다른 취약점 유형의 문제를 추가해 필요한 도구를 찾고, 모델이 직접 생성한 익스플로잇의 성공률과 도구 호출 수를 측정하는 것입니다. 이후 팀 브랜치를 병합하고 `main`에서 다시 실행해야 합니다.
